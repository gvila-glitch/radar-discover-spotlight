# X ingestion

- POST `/api/public/x-ingesta` requires managed cron bearer authentication before any reads or paid API call. Default body `{}`; manual test `{"ignorar_horario":true}` bypasses only hours.
- Uses explicitly requested plain Cloud `APIFY_TOKEN`, not a connector. Token travels only in Authorization, never in URLs, logs or responses.
- One synchronous Actor call, Spain input, maximum 30 trends, 120-second timeout including response body, no retries. Timeout may leave a paid Actor running on Apify: check Apify before another manual call.
- A durable non-waiting service-role-only RPC lock in reserved config rows covers preflight, paid call and save. Another execution returns `ejecucion_en_curso` without calling Apify. Owner-checked release runs in finally; no expiry or automatic takeover. If a process crashes, verify Apify/worker completion before clearing only the specific lock row. Existing table schemas are unchanged. Failed attempts do not consume the capture-based cap.
- Preflight: latest successful capture at least 45 minutes old, fewer than 20 distinct capture timestamps today in Madrid, configured Madrid hours unless manual override. Fail closed on read/config errors.
- Strict validation rejects empty/malformed lists. One atomic insertion stores only rank/name/category/postCount mappings; database default gives the batch one capture timestamp.
- 30-day cleanup appended to existing daily 03:00 UTC SQL job. X ingestion schedule: managed HTTP POST, `0 * * * *`, body `{}`; every hour at minute 00, all day, with Madrid hours checked by the function. Managed scheduler may spread delivery by approximately 30 seconds. Requires publication of the protected implementation before production can execute it.

## Concurrency verification
- Isolated PostgreSQL executes the applied lock RPCs across concurrent sessions; Apify is mocked, no provider call or cost. Two overlapping X executions make exactly one simulated provider call and save; the other skips. Two overlapping conversions act once with 7 existing alerts and a cap of 8; exactly one new entity and final total 8. Existing transactional cap/deduplication tests also pass.
- Lock release on failure, refusal of wrong-owner release and restricted RPC privileges verified. A crashed worker keeps the lock until verified manual recovery; this deliberately favors avoiding repeated paid calls over automatic recovery.
